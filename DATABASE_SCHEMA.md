# Balsathi AI — Target Data Model

## Status and conventions

This is a proposed Prisma/PostgreSQL model, not an applied migration. The required demo uses TypeScript objects with the same logical fields. A working PostgreSQL adapter, migration history, and seed command are follow-on deliverables unless completed and verified within the time box.

- Primary keys: UUIDs generated by the server or fixed UUIDs for synthetic fixtures.
- Calendar dates: PostgreSQL `date`, represented by Prisma `DateTime @db.Date` and serialized as `YYYY-MM-DD`.
- Timestamps: PostgreSQL `timestamptz`, represented by Prisma `DateTime @db.Timestamptz(3)` and serialized as UTC ISO timestamps.
- Use restrictive foreign-key deletion behavior. There is no record-delete endpoint in the MVP.
- Names, descriptions, and notes are plain text. No attachments, biometric data, government identifiers, addresses, or contact information are needed.

## Enumerations

| Enum | Values | Meaning |
| --- | --- | --- |
| `Role` | `WORKER`, `PARENT`, `ADMIN` | Seeded demo roles. |
| `Locale` | `en`, `hi`, `mr` | UI and template language. |
| `Concern` | `NONE`, `FOLLOW_UP` | Worker's explicit observation marker; not a clinical result. |
| `MilestoneDomain` | `MOTOR`, `LANGUAGE`, `SOCIAL` | Small illustrative grouping. |
| `MilestoneStatus` | `OBSERVED`, `NOT_OBSERVED` | An explicitly recorded milestone result. |

`NOT_RECORDED` is a read-model status for a missing milestone result, not a stored enum value.

## `User`

| Field | Type | Constraints/purpose |
| --- | --- | --- |
| `id` | UUID | Primary key. |
| `demoKey` | text | Unique, stable allowlisted selector such as `worker-a`; not a credential. |
| `displayName` | varchar(100) | Fictional display label. |
| `role` | `Role` | Required; assigned by seed data. |
| `preferredLocale` | `Locale` | Default `en`; browser choice may override display. |
| `createdAt` | timestamptz | Server default current time. |

There are no password, email, OTP, or external identity fields in this demo model. Demo login maps an allowlisted `demoKey` to this row.

## `Child`

| Field | Type | Constraints/purpose |
| --- | --- | --- |
| `id` | UUID | Primary key. |
| `displayName` | varchar(100) | Fictional label, for example “Demo child A”. |
| `dateOfBirth` | date | Required; not in the future. |
| `workerId` | UUID | Required foreign key to `User.id`. |
| `parentId` | UUID | Required foreign key to `User.id`. |
| `createdAt` | timestamptz | Server default current time. |

Indexes: `workerId`, `parentId`.

The service and seed validation must ensure `workerId` belongs to a worker and `parentId` belongs to a parent; ordinary foreign keys alone do not enforce roles. Records are seed-only in the MVP. One parent and one worker per child are deliberate simplifications.

## `Observation`

| Field | Type | Constraints/purpose |
| --- | --- | --- |
| `id` | UUID | Primary key; server generated. |
| `childId` | UUID | Required foreign key to `Child.id`. |
| `authorId` | UUID | Required foreign key to `User.id`; taken from the session. |
| `observedOn` | date | Between the child's date of birth and the current UTC date, inclusive. |
| `note` | varchar(1000) | Required; trim and require 1–1000 characters. |
| `concern` | `Concern` | Required; explicit form selection, default `NONE`. |
| `createdAt` | timestamptz | Server default current time. |

Index: `(childId, observedOn, createdAt)`.

Observations are append-only through the MVP API. Sort by `observedOn DESC`, then `createdAt DESC`, then `id` for deterministic display. The session user must be the child's assigned worker at write time. Parents and administrators cannot append observations.

## `MilestoneDefinition`

| Field | Type | Constraints/purpose |
| --- | --- | --- |
| `id` | UUID | Primary key. |
| `code` | varchar(64) | Unique, stable identifier. |
| `domain` | `MilestoneDomain` | Required. |
| `labelEn` | varchar(200) | English sample activity label. |
| `labelHi` | varchar(200) | Hindi sample activity label. |
| `labelMr` | varchar(200) | Marathi sample activity label. |
| `reviewAfterMonths` | integer | Nullable; non-negative when present. Illustrative review threshold only. |
| `sortOrder` | integer | Stable presentation order. |

Seed three simple, clearly illustrative activities with translated labels. Do not present these seed definitions or thresholds as an approved developmental assessment. Clinician-reviewed content, age windows, and content versioning are production work.

## `ChildMilestone`

| Field | Type | Constraints/purpose |
| --- | --- | --- |
| `id` | UUID | Primary key; server generated. |
| `childId` | UUID | Required foreign key to `Child.id`. |
| `milestoneId` | UUID | Required foreign key to `MilestoneDefinition.id`. |
| `status` | `MilestoneStatus` | Required. |
| `observedOn` | date | Required for `OBSERVED`; null for `NOT_OBSERVED`. |
| `recordedById` | UUID | Required foreign key to `User.id`; taken from the session. |
| `updatedAt` | timestamptz | Updated by the server on every upsert. |

Unique constraint: `(childId, milestoneId)`. This also supports reads by `childId`.

Upsert the current result atomically. Validate `observedOn` against birth date and the current UTC date. The assigned worker is the only writer. A last-write-wins current-state row is sufficient for the demo; an immutable assessment history and concurrency controls are production gaps. There is no “clear to unrecorded” operation in the MVP.

## Relationships

```text
User (WORKER) 1 ------ many Child via workerId
User (PARENT) 1 ------ many Child via parentId
Child         1 ------ many Observation
User          1 ------ many Observation via authorId
Child         1 ------ many ChildMilestone
MilestoneDefinition 1 - many ChildMilestone
User          1 ------ many ChildMilestone via recordedById
```

Administrator visibility is enforced by policy, not a direct child relationship. This model has no organization table and must not be used as a multi-tenant production design.

## Derived data: no additional tables

### Follow-up flags

Compute flags from the authorized child, its observations, its milestone results, and the current UTC date. Use rule version `demo-v1` and stable source-based identifiers.

- `OBSERVATION_FOLLOW_UP`: source is an observation explicitly marked `FOLLOW_UP`.
- `MILESTONE_REVIEW`: source is a recorded `NOT_OBSERVED` result whose illustrative review threshold has been reached.
- Unrecorded milestones produce no adverse flag.

Flags are advisory prompts, not diagnoses or validated risk scores. Observation flags remain present because the demo has no resolution workflow. A milestone flag disappears when its current result becomes `OBSERVED`.

### Sessions and assistant replies

Demo sessions are stored in a process-local map: opaque token, user ID, and fixed expiration time. They are not stored in PostgreSQL in this MVP. Assistant responses and prompts are not persisted.

## Repository parity and seed requirements

The demo repository must apply the same relationship filters, date validation, ID ownership checks, and milestone uniqueness behavior as the target PostgreSQL adapter. Copy returned objects or otherwise prevent callers from mutating store contents outside repository operations.

Seed only fictional data: two workers, two parents, one administrator, three children, three milestone definitions, and a few observations/results. Include a child outside each non-admin identity's scope, one unknown milestone, and one explicit follow-up case. Keep fixture UUIDs stable in both storage modes.

Before claiming PostgreSQL support, verify migration creation/application, foreign-key integrity, authorized reads and writes, unique milestone upserts, date round trips, and persistence across a restart. Database errors must not trigger silent fallback to in-memory data.
